## Day 1 — Meeting Room Booking System: Core Booking Logic & Data Structures

### Machine Coding: Design & Implement a Meeting Room Booking System (Part 1: Booking Engine)
- **Pattern / goal:** Implement conflict-free interval-based booking with in-memory storage; enforce overlap validation using half-open interval logic `[start, end)`.
- **Approach:**
  - Step 1 (~5 min): Parse requirements — rooms with capacity, bookRoom(startTime, endTime, requiredCapacity) must return bookingId or error; overlapping bookings forbidden; back-to-back [10,20) + [20,30) allowed.
  - Step 2 (~10 min): Design entities on paper: `Room` (roomId, capacity), `Booking` (bookingId, roomId, startTime, endTime, requiredCapacity), `Calendar` (per-room sorted bookings list for O(log n) overlap checks). Name the pattern: **Interval scheduling with conflict detection**.
  - Step 3 (~40 min): Implement in Java:
    - `Room` class with roomId, capacity, private getters.
    - `Booking` class immutable (final fields, sealed if possible).
    - `Calendar` class: maintain TreeMap<Long, List<Booking>> keyed by startTime OR use NavigableMap for range queries; implement `canBook(startTime, endTime)` checking overlap condition `startA < endB AND startB < endA`.
    - `Scheduler` service: `bookRoom(startTime, endTime, requiredCapacity)` — find first room with capacity ≥ required, call `calendar.canBook()`, if true create Booking and store.
    - Compile and test: bookRoom(10, 20, 5) should succeed; bookRoom(15, 25, 5) on same room should fail (overlap); bookRoom(20, 30, 5) should succeed (no overlap).
  - Step 4 (~15 min): Edge cases — null time inputs, negative capacity, zero-length intervals, capacity = 0, booking past/future times. Add input validation before any operation. Trace scenario: 3 rooms (ids 1,2,3 with capacities 5,10,15); book (10,20,7) → assigns room 2; book (10,20,12) → should fail on room 2, try room 3, succeed; book (20,30,7) → can reuse room 2.

## Day 2 — Meeting Room Booking System: Room Management & OOP Design

### Machine Coding: Design & Implement a Meeting Room Booking System (Part 2: Architecture & Encapsulation)
- **Pattern / goal:** Build clean, encapsulated room + scheduler architecture; enforce OOP principles (single responsibility, immutability, sealed interfaces) to make illegal states unrepresentable.
- **Approach:**
  - Step 1 (~5 min): Review requirements from Day 1; add focus: Room creation with roomId + capacity, Scheduler as main orchestrator, prevent double-booking at write time.
  - Step 2 (~10 min): Refine design on paper:
    - `Room` — immutable, sealed, final fields only.
    - `Booking` — immutable, sealed record or final class.
    - `Calendar` — encapsulates per-room sorted interval list; public method `isAvailable(startTime, endTime) → boolean`; private method `checkOverlap(start, end)`.
    - `Scheduler` — owns Map<String, Room>, Map<String, Calendar>; public interface: `createRoom(roomId, capacity)`, `bookRoom(roomId, startTime, endTime, requiredCapacity) → Booking`, `getBookings(roomId) → List<Booking>`.
    - Separate concerns: Scheduler handles room/booking lifecycle; Calendar handles interval logic; Room/Booking are value objects.
  - Step 3 (~40 min): Implement in Java:
    - `Room final class` — private capacity, immutable.
    - `Booking sealed class` — private startTime, endTime, roomId, capacity, immutable.
    - `Calendar class` — `NavigableMap<Long, Booking> bookings` sorted by startTime; `isAvailable(start, end)` uses `subMap()` to find overlaps in O(log n).
    - `Scheduler class`:
      - `createRoom(roomId, capacity)` — validate inputs, store Room, initialize Calendar.
      - `bookRoom(roomId, startTime, endTime, requiredCapacity)` — validate all inputs (null checks, positive times, end > start, capacity > 0), retrieve room, check capacity ≥ required, call calendar.isAvailable(), if false throw exception, if true create Booking, add to calendar, return booking.
      - No public mutators on Room/Booking; all state changes flow through Scheduler.
    - Compile and run: create rooms 1 (cap 5), 2 (cap 10); book(room2, 10, 20, 7) → success; book(room2, 15, 25, 5) → exception "Room unavailable"; book(room1, 10, 20, 6) → exception "Insufficient capacity".
  - Step 4 (~15 min): Edge cases and concurrency awareness:
    - Null input validation: throw `IllegalArgumentException` for null roomId, null/invalid times.
    - Duplicate roomId: throw exception on createRoom if roomId exists.
    - Time input: reject if startTime ≥ endTime, negative timestamps.
    - Concurrency: note that multi-threaded access could cause race conditions; discuss adding `synchronized` blocks on Calendar.isAvailable() + Booking creation, or use ConcurrentHashMap + ReentrantReadWriteLock for production.
    - Trace: Create rooms → book overlapping intervals → verify second booking rejects → book back-to-back → verify success.
