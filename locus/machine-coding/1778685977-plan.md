## Interview Strategy Notes

**For Locus SDE3 machine coding**, focus on:

1. **Extensibility over perfection** — show that adding a new vehicle type, new rate-limit strategy, or new assignment algorithm requires changing only 1–2 classes. SDE3 bar expects design that scales to 5+ new requirements mid-round.

2. **Concurrency & thread-safety** — Locus's platform runs at scale. Use `ConcurrentHashMap`, appropriate locks, or atomic variables. Don't just say "add synchronization" — actually implement it.

3. **SOLID principles** — especially **Open/Closed** (open for extension, closed for modification). Use interfaces and Strategy/State patterns liberally.

4. **Domain knowledge** — dispatch, routing, and logistics constraints are Locus's core. Show you understand capacity, time windows, zone affinity, and SLAs.

5. **Happy path first** — get a full end-to-end scenario working (order in → assignment → confirmation) before polishing edge cases. Working code beats beautiful design.

## Day 3 — Meeting Room Booking System (Core Scheduling Logic)

### Machine Coding: Meeting Room Booking System
- **Pattern / goal:** Design and implement a meeting room booking system with overlap detection, capacity validation, and clean entity modeling. Test ability to handle interval scheduling, enforce constraints, and avoid common pitfalls (missed validation, poor encapsulation, inefficient data structures).
- **Approach:**
  - **Step 1 (~5 min):** Clarify requirements: rooms have roomId and capacity; bookRoom(startTime, endTime, requiredCapacity) returns bookingId or error; two bookings overlap if startA < endB AND startB < endA; intervals are half-open [start, end) so [10,20) and [20,30) are adjacent, not overlapping. Identify entities: Room, Booking, Scheduler.
  - **Step 2 (~10 min):** Design data model: Room (roomId, capacity, immutable); Booking (bookingId, roomId, startTime, endTime, requiredCapacity, immutable VO); Scheduler (main orchestrator). For storage, sketch two approaches: (a) Map<roomId, List<Booking>> — simple but O(n) overlap check per booking; (b) Map<roomId, TreeMap<startTime, Booking>> — allows binary search but more complex. Start with (a) for clarity, note (b) as optimization.
  - **Step 3 (~50 min):** Implement core flow: (1) createRoom(roomId, capacity) — store in map, validate capacity > 0; (2) bookRoom(startTime, endTime, requiredCapacity) — find room with capacity ≥ requiredCapacity AND no overlap. **Critical:** validate overlap **before** adding booking — iterate existing bookings for the room, check if startTime < existingEnd AND existingStart < endTime; if true, skip this room; if no conflict found in chosen room, add booking and return bookingId. (3) getBookingsForRoom(roomId) — return sorted by startTime. Get happy path working: create room with capacity 10, book [10,20) and [20,30) both succeeding, book [15,25) failing.
  - **Step 4 (~15 min):** Edge cases: input validation (startTime >= endTime, requiredCapacity <= 0, null inputs), null room check, overlapping intervals at exact boundaries (e.g., [10,20) vs [20,30) must succeed, [10,20) vs [15,25) must fail), concurrent bookRoom() calls to same room (use synchronized map or lock on room object), no available room (return clear error message, not null). Trace scenario: book [10,20) succeeds; attempt [15,25) fails with "Room unavailable"; attempt [20,30) succeeds; list all bookings for room in order.
- **Time:** 90 min

## Day 4 — Meeting Room Booking System (Optimized Data Structures & Concurrency)

### Machine Coding: Meeting Room Booking System (Extended — Optimizations & Scalability)
- **Pattern / goal:** Refactor the booking system to use optimized data structures (TreeMap, interval trees), add proper thread-safety for concurrent bookings, and implement clean separation of concerns. Address common gaps: validation logic placed correctly, encapsulation enforced, concurrency handled.
- **Approach:**
  - **Step 1 (~5 min):** Review Day 3 implementation and identify bottlenecks: naive List iteration is O(n) per booking; no concurrency guard; validation mixed into service layer. Goal today: (1) optimize overlap detection to O(log n) using TreeMap or custom interval search; (2) add thread-safety; (3) split concerns (Scheduler validates, Repository stores, RoomService finds best room).
  - **Step 2 (~10 min):** Redesign: use Map<roomId, NavigableMap<Long startTime, Booking>> to store bookings sorted by start time. For overlap detection, given query interval [s, e), use ceiling(s) to find first booking at or after s; if it exists and its startTime < e, overlap found; otherwise no conflict. Alternatively, use a custom IntervalTree class (more complex but impressive). Add RoomRepository, BookingValidator, and RoomFinder as separate classes to isolate responsibilities.
  - **Step 3 (~50 min):** Implement optimized data structures: (1) Room and Booking POJOs with full encapsulation (private fields, getters, no setters). (2) BookingValidator — static method isOverlap(Booking a, Booking b) used in tests; validateInput(startTime, endTime, capacity) throws exceptions for invalid inputs. (3) RoomRepository — ConcurrentHashMap<String roomId, Room>; thread-safe add/get room. (4) BookingRegistry — Map<String roomId, NavigableMap<Long, Booking>> using ConcurrentSkipListMap for thread-safe sorted structure; findOverlappingBooking(roomId, interval) uses ceiling/floor logic. (5) Scheduler (or BookingService) orchestrates: call validator, find room with capacity and no overlap, add booking, return bookingId. Get it compiling and passing: create 2 rooms, concurrent book 5 orders across them, all succeed if non-overlapping, all fail if overlap detected.
  - **Step 4 (~15 min):** Edge cases & concurrency: (1) Two threads simultaneously book non-overlapping [10,20) and [20,30) — both must succeed; (2) Two threads simultaneously book overlapping [10,20) and [15,25) to same room — first wins, second gets error; (3) Concurrent add room while booking (use room get + check in single atomic operation if needed); (4) Invalid inputs: startTime > endTime, capacity 0 or negative, null roomId — all throw custom exceptions with clear messages. (5) Empty room case (no bookings yet — should always succeed if capacity OK). Trace scenario: 3 threads attempt to book room A simultaneously; overlapping bookings [10,20), [15,25), [20,30); expected: first thread succeeds, second fails, third succeeds; verify final booking list is correct and sorted.
- **Time:** 90 min
