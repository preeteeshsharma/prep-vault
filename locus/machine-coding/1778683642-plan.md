## Day 1 — Multi-stage System Design: Bank System

### Machine Coding: Design a Bank System with Multiple Functionalities
- **Pattern / goal:** Build a progressively unlocking 4-stage bank system that models accounts, transactions, constraints, and extensibility. This is the confirmed SDE2 question (Oct 2025); SDE3 will expect cleaner abstractions, better SOLID compliance, and deeper edge-case handling.
- **Approach:**
  - **Step 1 (~5 min):** Read and clarify the problem. Typical bank system scope: account creation, deposit, withdrawal, balance inquiry, transaction history, overdraft limits, concurrent access. Ask: Do we support multiple account types (savings/checking)? Multi-currency? Fraud detection? Start with core happy path only.
  - **Step 2 (~10 min):** Design on paper — sketch entities (Account, Transaction, User, Bank), key operations (deposit, withdraw, transfer), state invariants (balance ≥ 0 or ≤ overdraft limit), and immutable value objects (Money, TransactionId). Identify which class changes for each stage unlock.
  - **Step 3 (~40 min):** Implement Stage 1 (basic account + deposit/withdraw with balance checks). Compile and pass basic test cases. Then unlock Stage 2 (e.g., transaction history), Stage 3 (e.g., multi-account transfers with atomicity), Stage 4 (e.g., interest, overdraft, concurrent withdrawal). Ship working code; refactor only if time permits.
  - **Step 4 (~15 min):** Edge cases: concurrent deposits/withdrawals (use synchronized or locks), negative amounts, insufficient funds, transaction rollback, overdraft boundary. Trace one concrete scenario (e.g., two concurrent withdrawals that should fail atomically).
- **Time:** 90 min
- **Language:** Java (most common for system design at Locus given their engineering culture) or Python (if faster to iterate).
- **Success criteria:** All 4 stages compiling + basic test cases passing for each stage + clean separation of concerns (Account, Bank, Transaction classes distinct).

## Day 2 — Domain-Specific LLD: Maps & Location Services

### Machine Coding: Google Maps-based LLD Question
- **Pattern / goal:** Model a maps/location-based system (e.g., store locator, ride-sharing map, delivery tracking). Locus is a logistics company; this tests your ability to design spatial data structures, location queries, and real-world constraints. Expected at SDE3: geohashing or quadtree for performance, async event handling, fault tolerance.
- **Approach:**
  - **Step 1 (~5 min):** Clarify scope. Typical problem: find nearby stores/drivers within radius, track delivery in real-time, handle location updates concurrently. Confirm: single city or multi-region? Real-time or eventual consistency? Batch or streaming updates?
  - **Step 2 (~10 min):** Design on paper — entities (Location, Place/Driver, Query, SpatialIndex), key operations (addPlace, queryNearby, updateLocation). Choose a spatial index strategy: simple haversine + linear search (for <10k places), geohashing (for ~1M places), or quadtree (for hierarchical regions). Sketch the tradeoff for SDE3-level justification.
  - **Step 3 (~40 min):** Implement core happy path: location model with latitude/longitude, a spatial index (start with geohashing or simple distance calculation), addPlace, queryNearby. Get it compiling and passing basic cases (e.g., "find 3 stores within 5 km"). Then add concurrency (thread-safe location updates), caching (memoize recent queries), and extensibility (e.g., filter by category or rating).
  - **Step 4 (~15 min):** Edge cases: race conditions during concurrent location updates, cache invalidation on location change, queries spanning geohash boundaries, handling no results, performance on 1M+ locations. Trace one scenario (e.g., driver moves, nearby riders query returns stale data, then eventual consistency catches up).
- **Time:** 90 min
- **Language:** Java or Python.
- **Success criteria:** Core happy path working (add location + query nearby returns correct results) + thread-safe location updates + at least one optimization (geohashing OR quadtree OR caching) with justification + handles boundary/consistency edge cases gracefully.

- **Bank System (Day 1):** The Oct 2025 SDE2 candidate got a 4-stage unlock format. At SDE3, expect the same format but with stricter expectations: atomic multi-account transfers, no deadlocks, proper exception handling, and clean design patterns (Strategy for different account types, Builder for complex transactions). - **Maps LLD (Day 2):** Locus is a logistics startup — they care deeply about spatial queries and real-time updates. Show knowledge of geohashing (convert lat/lon to strings, prefix matching for nearby regions) or quadtree (recursive spatial partitioning). Justify your choice: geohashing is simpler to implement in 90 min; quadtree is more elegant but harder to code. Pick based on your confidence. SDE3 will be expected to reason about trade-offs clearly.

- **Both days:** Working code > perfect code. Get it compiling and passing basic cases first (Steps 1–3), then layer in edge cases (Step 4). Interviewers at Locus (outsourced to 3rd party) will test all test cases; if you fail early stages, you cannot unlock later ones. Prioritize correctness over cleverness.
