## Day 1 — Google Maps LLD (Domain-Aligned)

### LLD: Design a Google Maps-like System
- **Pattern / goal:** Model a real-world mapping/navigation system with location services, route calculation, and multi-stop planning. Emphasize extensibility for routing algorithm swaps and scale-out of geocoding.
- **Approach:**
  - **Phase 1 (Requirements, ~5 min):** Clarify scope — is this navigation-only or does it include geocoding, traffic, ETA? For SDE3, assume full feature set: user location tracking, multi-stop route optimization, ETA calculation, alternative routes. IN scope: routing, location objects, route storage. OUT scope: real-time traffic ML, map tile rendering.
  - **Phase 2 (Data models, ~3 min):** Immutable value objects: `Location` (lat/lon/address), `Route` (ordered waypoints), `Segment` (edge between two locations). Mutable entities: `NavigationSession` (current trip state), `RoutingCache` (computed routes).
  - **Phase 3 (Class & interface design, ~15 min):** Name the pattern *Strategy* for routing (Dijkstra vs. A* vs. custom optimization). Define sealed interfaces: `RoutingAlgorithm`, `GeocodingService`, `NavigationListener` (callbacks for route events). Build `NavigationEngine` as the facade. Check SOLID: SRP (one class = one responsibility: `RouteCalculator` handles algorithms only, `LocationManager` handles geo lookups). Show how adding a new routing heuristic requires only implementing `RoutingAlgorithm` (OCP).
  - **Phase 4 (Implementation & trace, ~10 min):** Implement happy path: user requests multi-stop route → `NavigationEngine` calls `RoutingAlgorithm.calculate(List<Location>)` → returns `Route` → notify listeners of ETA. Edge cases: invalid location (null check + throw exception), no route possible (return empty route or sentinel), rerouting on location deviation (detect via `LocationListener`, recalculate, notify).
  - **Phase 5 (Extensibility, ~5 min):** Show that adding traffic-aware ETAs only modifies `RoutingAlgorithm` implementation (inject `TrafficService`) — `NavigationEngine` and domain model stay unchanged.
- **Time:** 38 min

## Day 2 — Multi-Stage Machine Coding Problem (LLD + Code)

### LLD: Design a Multi-Stage Delivery Dispatch System (Staged Unlock Pattern)
- **Pattern / goal:** Model a staged delivery dispatch system where orders unlock new capabilities (Stage 1: single delivery, Stage 2: batch assignment, Stage 3: route optimization, Stage 4: real-time tracking). Code must pass test cases at each stage to unlock the next.
- **Approach:**
  - **Phase 1 (Requirements, ~5 min):** Clarify unlock criteria: Stage 1 — assign single delivery to a driver. Stage 2 — batch multiple deliveries, assign to one driver, no re-ordering allowed. Stage 3 — reorder deliveries within a batch (TSP/nearest-neighbor heuristic). Stage 4 — track driver location and update ETA dynamically. IN scope: order model, driver model, assignment logic, basic routing. OUT scope: payment, notifications, ML demand forecasting.
  - **Phase 2 (Data models, ~3 min):** Immutable: `Order` (id, source, destination, weight), `Driver` (id, location, capacity). Mutable: `Delivery` (order + assigned driver + status), `Batch` (list of deliveries), `DispatchSession` (current state + unlock flags).
  - **Phase 3 (Class & interface design, ~15 min):** Name the pattern *State* for multi-stage unlock (each stage = a state object with limited operations). Define `DispatchState` sealed interface with subclasses: `SingleDeliveryState`, `BatchAssignmentState`, `RoutingOptimizationState`, `TrackingState`. Define `OrderDispatcher` as the context that delegates to current state. Builder pattern for constructing orders with validation. Show SOLID: LSP (all states conform to `DispatchState` contract), ISP (each state only exposes relevant methods — `BatchAssignmentState` has `assignBatch()`, `SingleDeliveryState` does not).
  - **Phase 4 (Implementation & trace, ~10 min):** Implement Stage 1: `assignOrder(Order, Driver)` → validate driver capacity → create `Delivery` in ASSIGNED status → return success. Implement Stage 2: `assignBatch(List<Order>, Driver)` → calculate total weight → check capacity → create batch → unlock Stage 3. Stage 3: `optimizeRoute(Batch)` → use nearest-neighbor TSP → reorder deliveries → update route sequence. Stage 4: `updateTracking(Driver, Location)` → recalculate ETA for each remaining delivery → notify listeners. Edge cases: over-capacity (reject with exception), empty batch (return error), unroutable location (fallback to default order).
  - **Phase 5 (Extensibility, ~5 min):** Show that adding a new stage (Stage 5: customer preference optimization) only requires a new `PreferenceOptimizationState` class and wiring it to the state machine — no changes to dispatcher or data model.
- **Time:** 38 min
