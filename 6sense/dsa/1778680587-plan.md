- **Approach:**

### DSA: Palindromic Substrings (LeetCode 647)
- **Pattern / goal:** String manipulation + counting — identify and count all palindromic substrings efficiently.
- **Approach:**
  - Solve LeetCode 647 using expand-around-center (O(n²) time, O(1) space) — more efficient than DP for this problem.
  - Walk through: for each center (single char and between two chars), expand left and right while characters match.
  - Trace through "ababa" to confirm you count all 7 palindromes correctly.

### Sysdesign: Real-Time Messaging Platform
- **Pattern / goal:** Scalability, real-time delivery, and architecture for a messaging system (WhatsApp/Slack-like).
- **Approach:**
  - **Requirements:** 1M concurrent users, <500ms message delivery latency, persistence, offline message queue.
  - **Capacity:** ~1M messages/sec peak, each ~1KB; estimate storage for 30-day retention.
  - **API design:** `sendMessage(userId, targetUserId, text)`, `getMessages(userId, conversationId, limit)`, WebSocket for real-time subscription.
  - **Data model:** User, Message (immutable), Conversation, Chat session.
  - **Core components:** API gateway, WebSocket service, message queue (Kafka), database (PostgreSQL for transactional consistency), cache (Redis for active conversations), notification service.
  - **Deep dive:** Message delivery guarantee (at-least-once via Kafka + idempotency key in DB), handling offline users (queue messages in Redis, fetch on reconnect).
  - **Bottlenecks:** WebSocket scaling (use load balancer + sticky sessions), database write throughput (sharding by conversation ID).

## Day 2 — LLD, Advanced Sysdesign, & Behavioral

### LLD: Multi-Level Parking Lot System
- **Pattern / goal:** Class design with SOLID principles — model vehicles, levels, spots, and reservations for a scalable parking structure.
- **Approach:**
  - **Phase 1 (Requirements):** Support multiple levels, multiple spot types (compact, regular, handicap), vehicle entry/exit, spot reservation, price calculation, payment.
  - **Phase 2 (Data models):** Immutable VOs: `VehicleType`, `SpotType`, `ParkingTicket` (timestamp + lot ID + spot ID). Mutable: `ParkingSpot` (occupied flag, vehicle), `ParkingLevel` (spots array), `ParkingLot` (levels array, payment processor).
  - **Phase 3 (Class design):** Name pattern: **Strategy** for pricing, **Factory** for ticket creation. Sealed interface `PaymentMethod` (CreditCard, Cash). Method: `parkVehicle(vehicle, type)` → searches level → finds spot → returns ticket. Check SOLID: single responsibility (Spot only manages occupancy), open-closed (add new spot type without changing Spot).
  - **Phase 4 (Implementation):** Happy path: reserve spot → assign vehicle → generate ticket. Edge case: no spot available → throw exception. Trace: customer parks a regular car at 10am, stays 2 hours, pays $10.
  - **Phase 5 (Extensibility):** If requirement changes to "add dynamic pricing based on occupancy," only `PricingStrategy` class changes.
- **Time:** 40 min

### Sysdesign: Long-Running Workflow Execution (Apache Airflow Variant)
- **Pattern / goal:** Task scheduling and execution with idempotency — ensure certain workflow tasks execute only once per day at a given time, even if retried.
- **Approach:**
  - **Requirements:** Support DAG-like workflows, schedule specific tasks for once-daily execution, handle retries without duplicate execution, track task status, scalable for 1000s of concurrent workflows.
  - **Capacity:** ~10K workflows, ~100 tasks/workflow, task execution time 1–3600 sec; need idempotency for 24-hour window.
  - **API design:** `createWorkflow(taskList, schedule)`, `executeTask(taskId, workflowId)`, `getTaskStatus(workflowId, taskId)`.
  - **Data model:** `Workflow` (ID, taskList, createdAt), `Task` (ID, name, executionTime, dependencies), `TaskExecution` (taskId, workflowId, executedAt, status, idempotencyKey).
  - **Core components:** Scheduler (cron-like), worker pool (execute tasks), state store (PostgreSQL for task execution history), idempotency cache (Redis), message queue (RabbitMQ for task dispatch).
  - **Deep dive:** **Idempotency mechanism:** before executing a once-daily task, check Redis for `idempotencyKey = md5(workflowId + taskId + date)`. If key exists and value is "SUCCESS", skip execution. On first execution, set key + store execution record in DB. On retry within same day, check key and return cached result.
  - **Bottlenecks:** Scheduler must not re-schedule same task twice (use distributed lock on task ID + date), task completion notification must be reliable (use transactional outbox pattern).
- **Time:** 60 min
