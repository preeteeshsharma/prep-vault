## Day 1 — System Design & Core Architecture

### sysdesign: Design an Inverted Index / Search Engine System
- **Pattern / goal:** Build a scalable full-text search indexing system that supports fast retrieval and ranking — core to Moveworks' product for searching internal knowledge bases and tickets.
- **Approach:**
  - Phase 1 (5 min): Clarify scope — are we indexing documents, tickets, or knowledge articles? Real-time updates? How many documents? Query latency SLA?
  - Phase 2 (10 min): Capacity estimates — assume 10M documents, 100K queries/sec, index must fit in RAM or use distributed storage. Estimate inverted index size.
  - Phase 3 (15 min): Data model — design Document, Term, PostingList classes. Use sealed interfaces to enforce immutability for the index and mutability for the indexer.
  - Phase 4 (10 min): Happy path — tokenize a document, build the inverted index, execute a simple AND query. Trace how "find all tickets mentioning 'database' AND 'crash'" executes.
  - Phase 5 (5 min): Extensibility — show how ranking (TF-IDF, BM25) plugs in without touching the core index structure. How would you add phrase queries?
- **Time:** 60 min

### sysdesign: Design a Billing System
- **Pattern / goal:** Build a scalable billing and metering system that tracks usage (API calls, tickets indexed, active users) and generates invoices — critical for SaaS revenue in Moveworks.
- **Approach:**
  - Phase 1 (5 min): Clarify scope — what are the billable events? Per-user, per-ticket, per-API-call? Monthly or usage-based billing? Do we need real-time metering or batch processing?
  - Phase 2 (10 min): Capacity estimates — assume 10K customers, 1M billing events/day, invoices generated monthly. Estimate storage and processing load.
  - Phase 3 (15 min): Data model — design Meter, Event, UsageRecord, Invoice, Customer classes. Ensure immutability for audit trails; track state transitions clearly.
  - Phase 4 (10 min): Happy path — log a usage event, aggregate daily, generate an invoice. Trace a customer's monthly bill calculation including overage charges.
  - Phase 5 (5 min): Extensibility — show how a new pricing tier (e.g., tiered discounts) or a new billable metric plugs in. How would you support proration for mid-month plan changes?
- **Time:** 60 min

## Day 2 — Low-Level Design & Product Knowledge

### LLD: Design a Word / Hangman Guessing Game System
- **Pattern / goal:** Build a word-guessing game engine with state management, scoring, and turn management — tests your ability to handle stateful, turn-based systems similar to conversational AI flows in Moveworks.
- **Approach:**
  - Phase 1 (5 min): Restate requirements — players guess letters or full words. Limit guesses. Track wrong guesses. Declare win/loss. Single or multiplayer? Leaderboard?
  - Phase 2 (3 min): Data models — Game (mutable state), Word (immutable), Guess (immutable event), Player (mutable), ScoreBoard (mutable). Use sealed class hierarchies for GuessResult to prevent invalid states.
  - Phase 3 (15 min): Class design — name the pattern (State machine). GameState enum: SETUP → IN_PROGRESS → WON/LOST. GuessProcessor validates and applies guess, returns GuessResult (CorrectGuess | IncorrectGuess | InvalidGuess). Check SOLID: each class has one reason to change.
  - Phase 4 (10 min): Implement happy path — initialize game, process 3 correct guesses, win. Then edge case: exceed max guesses → loss. Trace a concrete game: "hangman" with guesses [h, a, n, g, m, a, n, x, z] → win after 7 guesses.
  - Phase 5 (5 min): Extensibility — to add "hint system," which single class changes? (HintProvider). To add "daily challenge leaderboard"? (ScoreBoard becomes persistent; GameSession references it).
- **Time:** 40 min

### LLD: Design Moveworks' Product Knowledge Base & Search Interface
- **Pattern / goal:** Model Moveworks' core feature: a searchable knowledge base for internal IT/HR automation, with relevance ranking and conversational context — reflects the actual product and tests your understanding of the company.
- **Approach:**
  - Phase 1 (5 min): Restate requirements — users (employees, IT staff) search for answers to common requests (password reset, software requests, time-off policies). Results ranked by relevance. Conversational context preserved across queries. Scope: single tenant or multi-tenant?
  - Phase 2 (3 min): Data models — KnowledgeArticle (immutable), Query (immutable event), SearchResult (immutable VO), UserSession (mutable), ConversationContext (mutable). Use sealed interface for QueryType to prevent invalid search types.
  - Phase 3 (15 min): Class design — name the pattern (Strategy for ranking; Observer for session context). SearchEngine orchestrates DocumentRetriever and Ranker. Ranker plugs in different strategies (TF-IDF, ML-based). SessionManager maintains ConversationContext. Check SOLID: each component has a single responsibility; SearchEngine doesn't know ranking details.
  - Phase 4 (10 min): Implement happy path — user searches "reset password" → SearchEngine retrieves top 5 articles → Ranker scores them → return ranked results. Edge case: user searches "my request from last week" → SessionManager looks up ConversationContext to infer intent. Trace: user session [Query: "password"] → [Query: "how long does it take?"] → system infers context and retrieves password-reset-time article.
  - Phase 5 (5 min): Extensibility — to add ML-based relevance ranking, which class changes? (Ranker strategy plugin). To support multi-language queries? (QueryNormalizer). To add feedback loop (thumbs up/down)? (FeedbackCollector → train ranker).
- **Time:** 40 min
