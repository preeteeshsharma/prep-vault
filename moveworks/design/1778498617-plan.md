## Day 1 — System Design Foundation & Enterprise Patterns

### sysdesign: Design an Idempotent Webhook Delivery System
- **Pattern / goal:** Build a reliable webhook dispatcher for Moveworks' conversation engine to notify downstream systems of actions (ticket creation, resolution, escalation). Focus on idempotency, retry logic, and delivery guarantees.
- **Approach:**
  - Requirements: Moveworks fires webhooks to customer integrations (Slack, Jira, ServiceNow, etc.). Must guarantee at-least-once delivery; support exponential backoff; handle timeout/failure scenarios; track delivery status.
  - Capacity: ~10K webhooks/sec, 99.99% delivery SLA, latency <2s p99.
  - Core components: webhook queue (Kafka/RabbitMQ), delivery worker pool, idempotency store (Redis), retry scheduler, DLQ for poison messages.
  - Deep dive: idempotency token generation and storage; how to detect duplicate deliveries on customer side; exponential backoff + jitter implementation.
  - Bottlenecks: customer endpoint slowness, network partitions, store failures.
- **Time:** 60 min

### LLD: Conversation State Machine & Intent Router
- **Pattern / goal:** Design the core state machine that tracks a multi-turn conversation in Moveworks (user message → NLU → intent routing → action execution → response). This is the foundation for product design questions later.
- **Approach:**
  - Phase 1 (5 min): Requirements — handle user utterances, route to intents (e.g., "create ticket", "check status"), track conversation context, support human escalation, log all state transitions for audit.
  - Phase 2 (3 min): Data models — `ConversationState` (user_id, turn_count, context_stack, current_intent); `Intent` (id, name, required_params, handler); `Message` (id, sender, text, timestamp, intent_detected).
  - Phase 3 (15 min): Class design — use **State pattern** for conversation states (AWAITING_INPUT → PROCESSING → RESPONSE_READY → SENT). Define sealed interface `ConversationState` with implementations: `AwaitingInputState`, `ProcessingState`, `EscalatedState`. Intent router as strategy pattern with pluggable intent handlers.
  - Phase 4 (10 min): Implement happy path — user sends message → router detects intent → state transitions → handler executes → response sent. Edge case: malformed intent, missing context, escalation trigger.
  - Phase 5 (5 min): Extensibility — show how adding a new intent (e.g., "report a bug") only requires a new `IntentHandler` and new state type; main conversation loop unchanged.
- **Time:** 40 min

## Day 2 — Product-Focused System Design & Advanced LLD

### sysdesign: Design a Conversation Intelligence Dashboard (Product/Feature Design)
- **Pattern / goal:** **This addresses the gotcha from real interviews**: Moveworks' second system design round often tests product design, not pure infrastructure. Design a dashboard where admins see conversation metrics, user satisfaction trends, resolution rates, and bot performance.
- **Approach:**
  - Requirements: Real-time metrics (conversation count, resolution rate, avg handling time, CSAT score), filtering by intent/user/time range, alerting on SLA breaches, export functionality. Multi-tenant (each customer sees only their data).
  - Capacity: 1K active dashboards simultaneously, metric updates every 5–10 sec, 1M conversations/day.
  - API design: `GET /dashboards/{dashboard_id}/metrics?intent=&time_range=`, `POST /dashboards/{id}/alerts`, `GET /metrics/export`.
  - Data model: time-series DB (InfluxDB/Prometheus) for metrics, metadata in PostgreSQL, materialized views for dashboard aggregations.
  - Core components: real-time metric aggregator, time-series store, caching layer (Redis), analytics worker.
  - Deep dive: how to compute rolling averages (e.g., 7-day CSAT) efficiently; cold data archival; handling schema changes for new intent types.
  - Bottlenecks: metric ingestion rate, dashboard query latency, multi-tenancy isolation.
- **Time:** 60 min

### LLD: Payment/Subscription Billing System (Extended Practice)
- **Pattern / goal:** Design a billing module for Moveworks' SaaS licensing (per-conversation, per-user-seat, or usage-based tiers). Moveworks integrates deeply with enterprise platforms; billing is mission-critical.
- **Approach:**
  - Phase 1 (5 min): Requirements — track usage (conversations, escalations, API calls), bill customers monthly, support multiple pricing tiers, handle credits/prorations, generate invoices, idempotent charge processing.
  - Phase 2 (3 min): Data models — `Subscription` (customer_id, tier, start_date, end_date, status); `UsageEvent` (customer_id, event_type, count, timestamp); `Invoice` (subscription_id, period, amount, status); `Charge` (invoice_id, idempotency_key, status, retry_count).
  - Phase 3 (15 min): Class design — use **Builder pattern** for invoice generation with complex pricing logic. Define sealed `BillingTier` interface with `StandardTier`, `PremiumTier`, `EnterpriseCustom`. Separate `UsageAggregator`, `PricingCalculator`, `ChargeProcessor` to keep responsibilities clear.
  - Phase 4 (10 min): Implement happy path — usage events stream in → aggregated daily → invoice generated at month-end → charge attempted → retry on failure. Edge case: customer downgrades mid-cycle (proration), duplicate usage events, payment failures.
  - Phase 5 (5 min): Extensibility — adding a new pricing tier only requires a new `BillingTier` impl; switching payment processor requires only new `PaymentGateway` impl; main billing loop unchanged.
- **Time:** 40 min

## Day 3 — Deep Dive: Distributed Tracing & Real-Time Sync

### sysdesign: Design a Distributed Conversation Tracing & Observability System
- **Pattern / goal:** Moveworks conversations involve multiple microservices (NLU, intent router, action executor, escalation handler, notification service). Design a tracing system to debug latency, failures, and user experience across the entire call chain.
- **Approach:**
  - Requirements: Trace every conversation from user message to bot response; capture latency per service; correlate logs/metrics; support sampling for high-volume traffic; queryable UI for engineers.
  - Capacity: 10K conversations/sec, trace size ~500 KB per conversation, 30-day retention.
  - Architecture: OpenTelemetry instrumentation across all services → trace collector (Jaeger backend) → time-series DB (Elasticsearch) → query/visualization layer.
  - API design: `POST /traces/ingest`, `GET /traces/{trace_id}`, `GET /services/{service}/latency_percentiles`.
  - Core components: trace collector, sampler (adaptive based on error rate), storage (Elasticsearch), query engine, UI.
  - Deep dive: how to sample 1% of high-volume traces while capturing 100% of errors; propagating trace context across async boundaries (Kafka); visualizing critical path in a span tree.
  - Bottlenecks: collector throughput, query latency on large time ranges, storage cost.
- **Time:** 60 min

### LLD: Real-Time Conversation Synchronization Across Clients (Product Feature)
- **Pattern / goal:** When a Moveworks user opens a conversation on web and then on mobile, both should stay in sync. Design the sync protocol and conflict resolution.
- **Approach:**
  - Phase 1 (5 min): Requirements — user sends message on web → bot responds → mobile client fetches latest state within 500 ms. If user types on both clients simultaneously, resolve conflict (last-write-wins or per-field merging). Support offline mode; sync when reconnected.
  - Phase 2 (3 min): Data models — `ConversationSnapshot` (conversation_id, version, messages, last_updated_at); `MessageDelta` (conversation_id, message_id, operation: ADD/DELETE/EDIT, timestamp); `SyncToken` (client_id, last_version_seen).
  - Phase 3 (15 min): Class design — use **Operational Transform (OT) or CRDT** principles. Define sealed `ConflictResolutionStrategy` with `LastWriteWins` and `FieldLevelMerge` implementations. `SyncManager` coordinates client updates with server state; `VersionStore` maintains version history for rollback.
  - Phase 4 (10 min): Implement happy path — client sends message with version token → server applies if version matches → broadcast delta to all other clients of same conversation. Edge case: network delay causes out-of-order messages; client offline; version mismatch triggers full resync.
  - Phase 5 (5 min): Extensibility — swapping conflict strategy only requires new `ConflictResolutionStrategy` impl; adding WebSocket as transport requires new `SyncTransport` impl.
- **Time:** 40 min

## Day 4 — Mock Interview & Weak Area Consolidation

### sysdesign: Mock Full Interview — Design a Conversation Routing System for Enterprise Escalations
- **Pattern / goal:** Simulate a real Moveworks system design interview. Design the system that decides when to escalate a conversation from bot to human agent, which agent pool to route to (based on skill, availability, language), and how to hand off context.
- **Approach:**
  - Full structure: Requirements (SLA tiers, agent availability, skill matching, fallback logic) → capacity planning (1M conversations/day, 500 agents, <30s queue time p95) → API design → data model → core components (escalation service, agent pool manager, skill matcher, context store) → deep dive on skill/language matching algorithm and multi-region failover → bottleneck analysis (queue latency, matcher throughput, state consistency).
  - This mirrors real Moveworks product logic and is highly likely to appear in an interview.
- **Time:** 60 min

### LLD: Mock Interview — Skill-Based Agent Routing & Queue Management
- **Pattern / goal:** Implement the core of the escalation routing system at the class level. How do you select the best agent for an incoming escalation?
- **Approach:**
  - Phase 1 (5 min): Requirements — route based on required skills (e.g., "billing expert", "Salesforce admin"), agent availability, language preference, SLA tier (VIP gets priority), load balancing.
  - Phase 2 (3 min): Data models — `Agent` (id, skills: Set<Skill>, language, status: AVAILABLE/BUSY/OFFLINE, current_load); `EscalationRequest` (required_skills, language, sla_tier, context); `Queue` (sla_tier, pending_requests).
  - Phase 3 (15 min): Class design — **Strategy pattern** for routing: `RoutingStrategy` with implementations `SkillBasedRouter`, `LoadBalancedRouter`, `SLABasedRouter`. Use **Priority Queue** for each SLA tier. Define sealed `AgentStatus` enum. Separate `SkillMatcher`, `AvailabilityChecker`, `LoadCalculator`.
  - Phase 4 (10 min): Implement happy path — escalation request arrives → find agents with required skills → rank by availability & load → assign to best → notify agent. Edge case: no agents available (add to queue), agent goes offline mid-conversation (re-route), skill set changes dynamically.
  - Phase 5 (5 min): Extensibility — adding a new routing strategy (e.g., "round-robin with skill affinity") only requires new `RoutingStrategy` impl; changing skill taxonomy only affects `SkillMatcher`.
- **Time:** 40 min
