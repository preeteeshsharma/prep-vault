## Day 3 — Low-Level Design: Core Patterns & SOLID

### LLD: Rate Limiter (Token Bucket / Sliding Window)
- **Pattern / goal:** Build a rate limiter to protect APIs from abuse — foundational design problem that surfaces OOP patterns.
- **Approach:**
  - Phase 1 (5 min): Requirements — limit by user ID, burst allowance, per-second / per-minute / per-hour. Scope: single machine first.
  - Phase 2 (3 min): Data models — `RateLimitBucket` (userID, capacity, refillRate, lastRefillTime), `Request` (userID, timestamp).
  - Phase 3 (15 min): Class design — name the pattern: **Strategy pattern for refill** (Token Bucket vs. Sliding Window). Create `RateLimiter` interface with `allowRequest(userID: string): boolean`. Implement `TokenBucketLimiter` with `refill()` and `consume()`. Use sealed interfaces to make invalid state transitions impossible (e.g., negative tokens should be unrepresentable).
  - Phase 4 (10 min): Happy path — user makes request → check tokens available → if yes, decrement and allow; if no, reject. Edge case: clock skew, concurrent requests. Trace: 3 requests allowed per second, user fires 5 → first 3 pass, next 2 rejected.
  - Phase 5 (5 min): Extensibility — swapping Token Bucket for Leaky Bucket: only constructor + algorithm change; `allowRequest()` signature unchanged.
- **Time:** 38 min

### LLD: Notification / Alert Delivery System
- **Pattern / goal:** Design a system to deliver notifications (email, SMS, Slack, push) with retries and persistence — mirrors Moveworks' alerting / escalation logic.
- **Approach:**
  - Phase 1 (5 min): Requirements — multiple channels, delivery guarantees (at-least-once), retry logic, dead letter queue.
  - Phase 2 (3 min): Data models — `Notification` (id, userID, content, channel, status, createdAt), `Channel` (email, sms, slack), `DeliveryAttempt` (notificationID, timestamp, status, error).
  - Phase 3 (15 min): Class design — name the pattern: **Strategy pattern for channels**, **Chain of Responsibility for retry logic**. Create `Channel` interface with `send(notification): Result`. Implement `EmailChannel`, `SMSChannel`, `SlackChannel` independently. Use sealed `DeliveryStatus` enum (PENDING, DELIVERED, FAILED, RETRYING) to prevent invalid state transitions.
  - Phase 4 (10 min): Happy path — notification enqueued → worker picks up → tries primary channel → on failure, add to retry queue with exponential backoff. Edge case: channel down, max retries exceeded, dead letter. Trace: send alert to user@example.com → SMTP timeout → mark RETRYING → wait 2s → retry → success.
  - Phase 5 (5 min): Extensibility — adding a new channel (e.g., Teams, Discord) requires only implementing `Channel` interface; core delivery loop untouched.
- **Time:** 38 min

## Day 4 — LLD Deep Dive & Edge Cases

### LLD: Message Queue / Pub-Sub System
- **Pattern / goal:** Design an in-memory or persistent queue for decoupling producers and consumers — critical for Moveworks' webhook delivery and workflow execution.
- **Approach:**
  - Phase 1 (5 min): Requirements — FIFO ordering, multiple subscribers per topic, message retention, ACK/NACK semantics.
  - Phase 2 (3 min): Data models — `Message` (id, topic, payload, timestamp, status), `Subscription` (subscriberID, topicID), `SubscriberOffset` (subscriberID, topicID, offset).
  - Phase 3 (15 min): Class design — name the pattern: **Observer pattern with offset tracking**. Create `MessageQueue` (main broker), `Topic` (collection of messages), `Subscriber` (listener with offset). Use sealed `MessageStatus` (QUEUED, DELIVERED, ACKNOWLEDGED, FAILED) to enforce state machine. Implement rebalancing when a subscriber joins/leaves.
  - Phase 4 (10 min): Happy path — producer publishes message → stored in topic → all subscribers notified → subscriber ACKs → offset advances. Edge case: subscriber crashes mid-processing, new subscriber joins (rebalance), message TTL expiry. Trace: publish "user.created" → 3 subscribers each receive → 2 ACK, 1 times out → retry logic kicks in.
  - Phase 5 (5 min): Extensibility — switching from in-memory to persistent storage (RocksDB, PostgreSQL) changes only the storage layer; Topic and Subscriber interfaces stay the same.
- **Time:** 38 min

### LLD: Job Scheduler / Task Executor
- **Pattern / goal:** Design a system to schedule and execute recurring or one-time jobs (cron-like) — underpins Moveworks' automation triggers.
- **Approach:**
  - Phase 1 (5 min): Requirements — recurring jobs (daily, hourly, cron), one-time delayed jobs, priority queue, failure handling + retries.
  - Phase 2 (3 min): Data models — `Job` (id, schedule, taskID, status, nextRunTime, retryCount), `TaskDefinition` (id, handler, params), `Execution` (jobID, startTime, endTime, status, error).
  - Phase 3 (15 min): Class design — name the pattern: **Factory pattern for job creation**, **State machine for job lifecycle**. Create `Scheduler` (main coordinator), `Job` (abstract with subclasses OneTimeJob, RecurringJob), `Worker` (executes tasks). Use sealed `JobStatus` (SCHEDULED, RUNNING, COMPLETED, FAILED, RETRYING) to prevent invalid transitions (e.g., COMPLETED → RUNNING should be impossible).
  - Phase 4 (10 min): Happy path — schedule "daily report" job at 9am → at 9am, Worker picks it up → executes task → logs result. Edge case: task times out, hits max retries, scheduler restarts (recover pending jobs from DB). Trace: job scheduled for 9am → 8:59am add to ready queue → 9:00am execute → success → next run 9am tomorrow.
  - Phase 5 (5 min): Extensibility — adding backpressure (max concurrent jobs) or changing retry strategy (exponential vs. fixed) requires only tweaking Worker and Job classes; core Scheduler loop unchanged.
- **Time:** 38 min

## Day 5 — System Design Deep Dive: Webhook Delivery

### sysdesign: Webhook Delivery System (Enterprise Scale)
- **Pattern / goal:** Design a robust webhook delivery pipeline that guarantees at-least-once delivery, handles retries, and supports millions of webhooks — directly relevant to Moveworks' integration layer.
- **Approach:**
  - Phase 1 (5 min): Clarify scope — single event or batch? Subscriber capacity? Retry SLA (how many times, what backoff)? Idempotency requirements?
  - Phase 2 (8 min): Capacity estimates — 100K subscribers, 1M webhook events/hour, avg payload 2KB, target delivery latency <5s.
  - Phase 3 (12 min): API design — `POST /webhooks/{subscriberID}` (register endpoint), `POST /events` (trigger webhook), `GET /webhooks/{id}/history` (delivery log). Data model: Webhook (subscriberID, URL, secret, status), Event (id, type, payload), Delivery (eventID, webhookID, attempts, status, lastError).
  - Phase 4 (20 min): Core components — event ingestion (Kafka), delivery worker (HTTP client with timeout), retry queue (exponential backoff: 1s, 2s, 4s, 8s, 16s, then DLQ), idempotency store (deduplicate by event ID + subscriber), monitoring (delivery success rate, latency P99). Trace: event fired → enqueue to Kafka → worker fetches → POST to subscriber URL → 200 OK → mark delivered; if timeout → add to retry queue with delay.
  - Phase 5 (5 min): Extensibility — swapping HTTP for gRPC, adding circuit breaker per subscriber, or adding webhook signing (HMAC-SHA256) should not require changes to core delivery state machine.
- **Time:** 50 min
